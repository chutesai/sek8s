# Feature Spec: X-Signature Attestation Response Header

**Date**: 2026-04-30  
**Status**: draft

---

## Context

Third-party attestation flow: client -> validator API -> attestation-proxy (k3s, external port 8443) -> chute instance via `/service/{name}/{path}`. The response currently includes TDX/NVIDIA evidence and the public TLS cert (read by the validator from the TLS handshake), but there is no cryptographic proof that the entity serving the response actually holds the private key for that cert. An attacker who intercepted the response could substitute evidence from a different machine alongside a different cert without detection.

The attestation proxy already terminates TLS using the host-generated cert/key pair mounted from `/etc/attestation-service/certs/` into the pod at `/etc/ssl/host-certs/`. The TDX quote's report data already embeds a SHA-256 hash of this cert's public key, binding the quote to the cert. The missing link is proving the responder possesses the corresponding private key.

- **Packages affected**: `attestation-proxy`
- **Key files**: `src/attestation-proxy/attestation_proxy/service.py`, `src/attestation-proxy/attestation_proxy/config.py`, `src/attestation-proxy/pyproject.toml`
- **Dependencies**: `cryptography` (already in lockfile as transitive dep via `substrate-interface`; will be declared as explicit dep)

---

## Design Decisions

- **Sign in the attestation proxy, not the host attestation service.** The proxy is the publicly accessible entrypoint, has the host certs mounted, and is the natural place to attach response headers. The host attestation service communicates only over a Unix socket.
- **Sign ALL proxied responses**, not just attestation ones. RSA signing a response body is cheap (~1ms for 4096-bit key) and makes the proxy's identity provable on every response. Clients that don't need the header can ignore it.
- **RSA-PKCS1v15 with SHA-256.** Matches the 4096-bit RSA key generated by `setup-tls-certs.sh`. PKCS1v15 is the most widely supported RSA signature scheme for verification across languages.
- **Base64 encoding** for the header value -- standard practice for binary data in HTTP headers.
- **No new config fields.** The private key path is already available via `TLS_KEY_PATH`.
- **Load the key once at startup.** The private key is read from disk during `SharedProxyResources.initialize()` and held in memory. No per-request file I/O.

---

## API Changes

- **New endpoints**: None.
- **Schema changes**: None. The `AttestationResponse` model is unchanged.
- **Migrations**: None.
- **New response header**: `X-Signature` -- base64-encoded RSA-PKCS1v15-SHA256 signature over the raw response body bytes. Present on all proxied responses from both `/server/` and `/service/` routes.

---

## Goal

Success = clients receiving attestation responses can cryptographically verify the full trust chain:

1. `X-Signature` header is present on every proxied response from the attestation proxy.
2. Verifying `RSA_VERIFY(public_cert, base64_decode(X-Signature), response_body)` succeeds, proving the responder holds the private key.
3. Combined with the existing TDX report data binding (cert public key hash in report data), the full chain is: signature proves key possession -> cert hash in TDX report data matches cert -> TDX quote is hardware-attested.
4. No private key material is ever exposed in pod logs.
5. If the private key is unavailable at startup, the proxy logs a warning and continues without signing (responses omit the header rather than failing).

---

## Constraints

- **No key material in logs.** Miners can read pod logs but cannot exec into the pod. Never log private key bytes, PEM content, key object repr, or file contents. Safe to log: key file path, key type/size (e.g. "Loaded 4096-bit RSA key"), success/failure status.
- **Graceful degradation.** If the private key cannot be loaded, the proxy must still function -- responses simply omit the `X-Signature` header. This is a warning, not a fatal error.
- **No new dependencies beyond `cryptography`**, which is already in the lockfile.
- **No changes to the host attestation service** (`src/sek8s/`), Ansible roles, or k8s manifests.

---

## Output Format

1. `src/attestation-proxy/attestation_proxy/signing.py` (new) -- `load_private_key(path) -> RSAPrivateKey | None` and `sign_response_body(key, body) -> str` functions. Key loading logs path + key metadata only. Returns `None` on failure with a logged warning.
2. `src/attestation-proxy/attestation_proxy/service.py` (modify) -- `SharedProxyResources` gains a `private_key` attribute populated in `initialize()`. `BaseProxyServer.proxy_request()` calls `sign_response_body()` and adds `X-Signature` to response headers when the key is available.
3. `src/attestation-proxy/pyproject.toml` (modify) -- add `cryptography` as explicit dependency.
4. `tests/unit/test_attestation_proxy_signing.py` (new) -- unit tests for signing round-trip (sign + verify), header presence in proxied responses, graceful degradation when key is absent.

---

## Failure Conditions

- Private key bytes, PEM content, or file contents appear in any log output.
- `X-Signature` header contains a value that does not verify against the public cert and response body.
- Proxy crashes or refuses to start when the private key file is missing or malformed.
- Signing modifies the response body (signature must be computed over the unmodified upstream response).
- The header is silently dropped by the proxy's hop-by-hop header filtering (must not be in the strip list).
- Signing introduces measurable latency (>10ms per request) for typical attestation response sizes.

---

## Rollout Notes

- No Ansible, k8s manifest, or host-side changes required. The private key and cert are already mounted into the attestation-proxy pod via `hostPath` volume.
- The feature is automatically active when the proxy starts with a valid `TLS_KEY_PATH`. No feature flag needed.
- Validators / clients will need to be updated to read and verify the `X-Signature` header. Until then, the header is harmlessly present and ignored.
- Backward compatible: existing clients that don't check `X-Signature` are unaffected.
- Version bump: `src/attestation-proxy/VERSION` per versioning policy.
